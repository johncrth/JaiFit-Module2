# Feature List — JaiFit MVP

สรุปฟีเจอร์ทั้งหมดของ JaiFit MVP จัดลำดับความสำคัญแบบ MoSCoW แปลงมาจาก [[../01-spec/20260827-01-jaifit-ai-coach-metabolic-transition|Requirement Spec]] และ [[../backlog|Product Backlog]]

> Priority ที่ทำเครื่องหมาย *(ประเมิน)* หมายถึงยังไม่มีการยืนยันชัดเจนใน spec/backlog ต้นทาง เป็นการประเมินตามผลกระทบต่อปัญหาหลัก (dropout ช่วง metabolic transition วันที่ 1-7) — ควรให้ผู้ใช้/สปอนเซอร์ยืนยันก่อนนำไปวาง roadmap จริง

## กลุ่ม A — เก็บข้อมูลพฤติกรรมการกิน

| Feature ID | ชื่อฟีเจอร์ | คำอธิบาย | Priority | อ้างอิง |
|---|---|---|---|---|
| F1 | บันทึกพฤติกรรมผ่านบทสนทนาอิสระ | User พิมพ์/คุยกับ AI แบบธรรมชาติผ่านหน้าแชทบน Web App แทนการกรอกฟอร์ม เพื่อบอกว่ากินอะไรไปเมื่อไหร่ | Must | FR1, E1-01 |
| F2 | สกัด pattern เวลา/เมนู/ความถี่จากบทสนทนา | AI ดึงข้อมูลเวลา เมนู/ประเภทอาหาร และความถี่ ออกจากข้อความอิสระของ user | Must | FR1, E1-02 |
| F3 | ถามกลับเมื่อข้อมูลกำกวม | เมื่อ AI สกัดข้อมูลไม่ชัดเจน ต้องถาม clarifying question แทนการเดา | Should | FR1, E1-03 |
| F4 | ปรับปรุง behavior profile ต่อเนื่อง | Pattern ของ user ถูกอัปเดตทุกครั้งที่มีข้อมูลใหม่เข้ามา ไม่ใช่คำนวณครั้งเดียว | Should | FR1, E1-04 |

|---|---|---|---|---|

| F7 | จำกัดเพดานจำนวน nudge ต่อวัน แบบปรับอัตโนมัติตาม phase | ป้องกันไม่ให้ user รำคาญจากข้อความที่ถี่เกินไป — phase หนักส่งถี่กว่า, phase คงตัวส่งห่างกว่า (ยืนยันแล้ว — เดิม open question 10.3; ค่า threshold ตัวเลขจริงต่อ phase ยังกำหนดตอน implement) | Should | FR2, E2-03 |
| F8 | ตั้ง default เวลาส่งล่วงหน้าอัตโนมัติ + ปรับเองได้ | ระบบตั้ง default 15-30 นาทีก่อนเวลาเสี่ยงให้ทุก user ตั้งแต่แรก และ user ปรับเวลาเองได้ภายหลังในหน้าตั้งค่า (ยืนยันแล้ว — เดิม open question 10.1) | Should | FR2, E2-04 |

Open Questions 10.1-10.4, 10.6-10.13 ของ spec ต้นทางถูกปิดแล้ว (ดู [[../../05-log/20260829-log|log 2026-08-29]]) — รายการด้านล่างอัปเดตให้สะท้อนสถานะล่าสุด เหลือเฉพาะ 10.5 (baseline metric) ที่ยังเปิดอยู่และไม่กระทบ feature list นี้โดยตรง:

- ~~Priority ของ F7, F8, F13~~ — ปิดแล้ว: F7 ปรับอัตโนมัติตาม phase, F8 ตั้ง default 15-30 นาที + ปรับเองได้ (เลื่อนเป็น Should), F13 ใช้ detection แบบผสม — ค่า threshold ตัวเลขจริง (กี่นาที/กี่ครั้งต่อ phase) ยังต้องกำหนดตอน implement
- F9, F10 อิงกับตาราง phase ในหัวข้อ 8 ของ spec ซึ่งเป็นสมมติฐานที่ยังไม่ผ่านการ validate จากนักโภชนาการ/แพทย์ — ยืนยันแล้วว่าใช้สมมติฐานนี้ไปก่อนใน MVP (เดิม open question 10.4) แต่ยังเป็นความเสี่ยงสูงสุดของ Feature List นี้เพราะกระทบสุขภาพ user โดยตรง — ผ่อนคลายความเสี่ยงบางส่วนด้วย F40-F44 (คัดกรองโรคประจำตัว + ผ่อนปรนตามอาการ)
- F11 กับ F15 มีเนื้อหาคาบเกี่ยวกัน (แสดง phase ปัจจุบัน) — ตอนออกแบบ UI จริงอาจรวมเป็นองค์ประกอบเดียวกันในหน้า dashboard ได้ ไม่จำเป็นต้องแยกเป็น 2 ส่วนของหน้าจอ
- ~~F21 (เปลี่ยนโหมดภายหลัง)~~ — ปิดแล้ว: เปลี่ยนได้ตลอดเวลาไม่จำกัดจำนวนครั้ง (เลื่อนเป็น Must) แต่ต้องมี F39 (อธิบายผลลัพธ์ก่อนเปลี่ยน) คู่กันเสมอ
- F24, F25 (เตือนล่วงหน้า) อิงเนื้อหาจากสมมติฐานประสบการณ์ผู้ก่อตั้งเช่นเดียวกับตาราง phase — ยืนยันแล้วว่าใช้สมมติฐานนี้ไปก่อนใน MVP (เดิม open question 10.8) แล้วปรับตาม feedback จริงภายหลัง
- F26-F29 (Reward System) priority "Must" เพราะ insight ระบุว่าเป็นแรงจูงใจระยะยาวสำคัญ — กติกาการนับ/รีเซ็ต streak ยืนยันแล้ว (เดิม open question 10.9): มี grace day 1 วันก่อนตัดจริง
- F31 (จัดกลุ่มระดับความเข้มแข็งทางใจ) ยืนยันแล้ว (เดิม open question 10.10): ใช้ 4 กลุ่มจากประสบการณ์ผู้ก่อตั้งเป็นฐาน แต่ AI มีความยืดหยุ่นประเมินจากบทสนทนาจริงได้ ไม่ยึดติดตายตัว 100% — ยังไม่ผ่านการ validate จากนักจิตวิทยา/ผู้เชี่ยวชาญ
- F30 (เก็บแรงจูงใจตอน onboarding) ยืนยันแล้ว (เดิม open question 10.11): กลุ่มแรงจูงใจเข้มแข็งไม่ถามซ้ำ, กลุ่มอ่อนกว่าถามทบทวนเป็นระยะหลังได้รับ reward (F27/F28) — F33 (โยงข้อความกลับแรงจูงใจ) ยังเป็น Should ตามเดิม
- F37 (ขอสิทธิ์ Web Push) ยืนยันแล้ว (เดิม open question 10.12): fallback ไป Email ทันทีแบบไม่ถามซ้ำ ไม่เพิ่มช่องทางอื่นนอกเหนือ Web Push/Email
- F36 (เข้าสู่ระบบ/session) ยืนยันแล้ว (เดิม open question 10.13): ใช้ JWT Token + รองรับ Google Sign-In และ Email/Password
- F40-F44 (Chronic Condition Screening, Adaptive Symptom Easing) เป็นฟีเจอร์ใหม่จากการปิด open question 10.4 — ยังไม่มี UX flow ละเอียดว่าจะถามโรคประจำตัวแบบ conversational หรือฟอร์มปิด และยังไม่กำหนดเกณฑ์ตัวเลขที่ชัดเจนว่า "อาการแย่ลงมาก" คือระดับไหน ต้องออกแบบเพิ่มในขั้น detailed design
