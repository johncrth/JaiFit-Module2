## 1. ภาพรวมโปรเจกต์ (Overview)

JaiFit คือ AI Coach ส่วนตัวที่ทำงานผ่าน **Web App (เว็บแอปพลิเคชัน Full-Stack)** มีเป้าหมายเพื่อประคอง user ให้ผ่านช่วง **เปลี่ยนระบบเผาผลาญ (metabolic transition)** ตอนเริ่มลดน้ำหนักแบบ low-carb/keto ไปได้ โดยเฉพาะ 1-7 วันแรกซึ่งเป็นช่วงที่คนส่วนใหญ่ล้มเลิก

จุดต่างจากแอปลดน้ำหนักทั่วไป: JaiFit ไม่ได้เน้นการนับแคลอรี่หรือให้ user กรอกฟอร์มยาวๆ แต่เน้น **ทำนายพฤติกรรมล่วงหน้าและเข้าไปแทรกแซง (proactive) ก่อนจะเผลอกิน** พร้อมดูแลสภาพจิตใจในช่วงที่ร่างกายอ่อนล้าจากอาการถอนน้ำตาล

> **หมายเหตุการเปลี่ยนช่องทาง (2026-08-28):** เอกสารฉบับก่อนหน้าออกแบบ JaiFit เป็น LINE Official Account bot แนวคิดฟีเจอร์และ data flow ทั้งหมด (การเก็บพฤติกรรมการกิน, proactive nudge, phase tracking, โหมดความเข้มข้น, Reward System, Motivation Profiling) **ยังคงไว้เหมือนเดิมทุกจุด** — สิ่งที่เปลี่ยนคือ **ช่องทางที่ user ใช้งาน** จากแชท LINE เป็น **หน้าเว็บ (Web App)** แทน เนื่องจากเป็นข้อกำหนดของหลักสูตร ADT-RAISE ที่กำหนดผลงานปลายทางเป็น "Web App Full-Stack + AI, Deploy จริง" และ Module 2 ของหลักสูตรสอน Full-Stack ด้วย Node.js/Git เป็นหลัก — รายละเอียดเหตุผลและผลกระทบต่อเอกสารทั้งชุด ดู [[../../05-log/20260828-03-log|log 2026-08-28 รอบ 3]]

## 2. ปัญหา (Problem Statement)

- คนที่มีน้ำหนักเกิน 100 กก. (Body Fat > 30%) ที่ลองลด low-carb/keto ล้มเลิกกลางทางสูงถึง **90%**
- สาเหตุหลักไม่ใช่การขาดวินัย แต่เป็น **อาการถอนน้ำตาล (carb withdrawal)** ในช่วง 1-7 วันแรกของการเปลี่ยนระบบเผาผลาญ เช่น มือสั่น มึนหัว หงุดหงิด อ่อนเพลีย ซึ่งเป็นอาการทางสรีรวิทยาที่คาดเดาได้
- เครื่องมือลดน้ำหนักที่มีอยู่ในตลาด (นับแคลอรี่, log อาหารย้อนหลัง) เป็นเครื่องมือ **เชิงรับ (reactive)** — บันทึกหลังกินไปแล้ว ไม่ได้ช่วยดักไว้ก่อนตัดสินใจกินของต้องห้าม

## 3. กลุ่มเป้าหมาย (Target Users)

- น้ำหนักเกิน 100 กก. และ Body Fat > 30%
- เคยพยายามลดน้ำหนักมาก่อนแต่ไม่สำเร็จ (อย่างน้อย 1 ครั้ง)
- กำลังเริ่มหรือกำลังพิจารณาลดน้ำหนักแบบ low-carb/keto
- ใช้งานอินเทอร์เน็ต/เว็บเบราว์เซอร์เป็นประจำในชีวิตประจำวัน (ผ่านมือถือหรือคอมพิวเตอร์)

### Persona ตัวอย่าง
> "คุณเอ" อายุ 35 ปี น้ำหนัก 115 กก. เคยลด keto มาแล้ว 2 ครั้งแต่เลิกกลางทางทั้งคู่ในสัปดาห์แรก เพราะมือสั่นระหว่างประชุมจนต้องกินขนมปังเพื่อให้หายมึน แล้วรู้สึกผิดจนเลิกไปเลย

| Reward System กระตุ้นความต่อเนื่อง | % ของ user ที่ทำ streak ครบ 7 วันต่อเนื่อง (ปลดล็อก cheat meal) และครบ 30 วันต่อเนื่อง (ปลดล็อก cheat day) |
| ข้อความให้กำลังใจตรงกับแรงจูงใจของ user | % ของข้อความให้กำลังใจที่โยงกลับไปหา motivation profile ของ user (เช่น อ้างถึงคนที่รัก/เป้าหมายที่ user ระบุไว้) |

| ความถี่เปลี่ยนโหมดความเข้มข้น (10.6) | **เปลี่ยนได้ตลอดเวลา ไม่จำกัดจำนวนครั้ง** (ยืดหยุ่นสูงสุด) แต่ระบบต้องอธิบายผลลัพธ์ที่จะได้รับให้ user เข้าใจก่อนเปลี่ยนทุกครั้ง (เช่น เปรียบเทียบผลลัพธ์เร็ว/ช้าตามหลักการ "อ้วนก็ไม่ได้อ้วนในวันสองวัน การลดก็ไม่ควรคาดหวังผลในวันสองวันเช่นกัน") |
| กลไกหมุนเวียนข้อความ (10.7) | ใช้แบบผสม — มี **content library** เป็นฐานข้อความ แล้วให้ **AI ปรับถ้อยคำ/มุมมองให้เข้ากับ context ของ user แต่ละคน** (ตรงกับแนวทางที่ 3 เดิม) |
| เนื้อหาการเตือนล่วงหน้า (10.8) | ใช้สมมติฐานเบื้องต้นจากประสบการณ์ผู้ก่อตั้งไปก่อนใน MVP แล้วปรับตาม feedback จริงภายหลัง (ตรงกับแนวทางที่ 1 เดิม — เหมือนแนวทางเดียวกับตาราง phase) |
| กติกา reset streak (10.9) | ให้ streak **พักได้ 1 วันโดยไม่ถูกตัด (grace day)** ก่อนจะตัดจริง เป็นแนวทางผ่อนปรนที่ไม่ตัดสิน user (ตรงกับแนวทางที่ 3 เดิม) |
| การจัดกลุ่มความเข้มแข็งทางใจ (10.10) | ใช้ **4 กลุ่มเดิม**จากประสบการณ์ผู้ก่อตั้งเป็นฐาน (ถูกบังคับ/กลัวจากข่าว/เพื่อคนที่รัก/ตระหนักด้วยตัวเอง) **แต่ให้ AI มีความยืดหยุ่นประเมินระดับความเข้มแข็งจากบทสนทนาจริงได้** ไม่ยึดติดตายตัว 100% (ผสมแนวทางที่ 1 กับความยืดหยุ่นบางส่วนของแนวทางที่ 3 เดิม) |
| การถามทบทวนแรงจูงใจซ้ำ (10.11) | User ที่มีแรงจูงใจกลุ่ม**เข้มแข็ง** (เพื่อคนที่รัก, ตระหนักด้วยตัวเอง) ใช้ค่าที่เก็บตอน onboarding ตลอดโปรแกรม **ไม่ถามซ้ำ** — user ที่มีแรงจูงใจกลุ่ม**อ่อนกว่า** (ถูกบังคับ, กลัวจากข่าว) ให้ AI **ถามทบทวนเป็นระยะ** โดยจังหวะที่เหมาะสมคือ**หลังจาก user ได้รับ reward จาก Reward System (FR9)** |
| นโยบาย fallback การแจ้งเตือน (10.12) | ตัดช่องทาง LINE ออก ใช้เฉพาะ **Web Push Notification เป็นช่องทางหลัก** และ **Email เป็นช่องทางสำรอง** ตามที่ตัดสินใจไว้เดิมใน FR2 — ไม่เพิ่มช่องทางอื่น |
| เทคนิค Authentication (10.13) | ใช้ **JWT Token** เป็นกลไกหลัก (เหมาะกับ React+Node.js ที่แยก Frontend/Backend) และรองรับ **2 วิธีสมัคร/เข้าสู่ระบบ**: **Google Sign-In (OAuth)** และ **Email/Password** แบบดั้งเดิม ให้ user เลือกได้เอง — ดู FR11 |

> **หมายเหตุอนาคต (Native Mobile App):** ในอนาคตอาจพิจารณาขยายเป็น **Native Mobile App (iOS/Android)** ในเฟสถัดไป โดย Backend/API/Database ที่ออกแบบไว้ควรคงหลักการแยกอิสระจาก Frontend (ตามสถาปัตยกรรม REST API ที่ตัดสินใจไว้แล้ว) เพื่อให้รองรับการเพิ่ม native app client ในอนาคตได้โดยไม่ต้องรื้อ backend ใหม่ — **ยังไม่ใช่การตัดสินใจหรือรายละเอียดที่ต้อง implement ตอนนี้** เป็นเพียงหมายเหตุเชิง constraint ให้ทีมเทคนิคคำนึงถึงตอนออกแบบ

## 6. ขอบเขต (Scope)

### อยู่ในขอบเขต (In Scope — MVP)
0. **สมัครสมาชิก/เข้าสู่ระบบ (Account Signup & Login)** ด้วยอีเมล + รหัสผ่าน เพื่อระบุตัวตน user บน Web App (โครงสร้างพื้นฐานที่จำเป็นแทน LINE user ID เดิม)
1. เก็บข้อมูลพฤติกรรมการกินผ่านหน้าเว็บแอป (แชท/ช่องข้อความอิสระบนเว็บ) — เวลาที่มักกินของหวาน/แป้ง, เมนูโปรด
2. AI ส่ง proactive nudge ก่อนถึงช่วงเวลาเสี่ยง พร้อมเสนอทางเลือกทดแทนเฉพาะเจาะจงต่อ user
3. ระบบติดตาม phase ของการเปลี่ยนระบบเผาผลาญแบบ fixed calendar-based และปรับโทนข้อความตาม phase
4. ข้อความให้กำลังใจ + อธิบายอาการถอนน้ำตาลว่าเป็นเรื่องปกติ ในช่วงวันที่หนัก
5. ระบบเสนอ "cheat meal ที่ควบคุมได้" ที่ไม่ทำลายการเปลี่ยนระบบเผาผลาญ
6. Dashboard สรุปความคืบหน้าแบบง่าย (weekly summary)
7. ให้ user เลือก **โหมดความเข้มข้นในการปรับพฤติกรรม** ตอนเริ่มใช้งาน (หักดิบ / ค่อยเป็นค่อยไป) และปรับจังหวะ/เนื้อหาข้อความตามโหมดที่เลือก
8. AI **สื่อสารด้วยวิธีที่หลากหลาย ไม่ซ้ำเดิม** ทั้งคำแนะนำเมนูทดแทนและข้อความให้กำลังใจ เพื่อรักษาความต่อเนื่องของ user
9. AI **เตือนล่วงหน้าเรื่องอาการ/สถานการณ์ไม่พึงประสงค์ที่อาจเกิดขึ้น** พร้อมวิธีรับมือ ไม่ใช่สื่อสารด้านบวกอย่างเดียว
10. **Reward System** — ปลดล็อก cheat meal/cheat day เมื่อ user ทำตามแผนต่อเนื่องถึง milestone ที่กำหนด (7 วัน → cheat meal ควบคุมได้, 30 วัน → cheat day เต็มวัน)
11. **Motivation Profiling** — เก็บข้อมูลแรงจูงใจ/สาเหตุที่ user อยากลดน้ำหนักตอน onboarding และใช้ปรับโทน/ความถี่การสื่อสาร รวมถึงโยงข้อความให้กำลังใจกลับไปหาแรงจูงใจเดิมของ user
12. **Chronic Condition Screening** — คัดกรองว่า user มีโรคประจำตัว (ความดัน, เบาหวาน ฯลฯ) หรือไม่ตอน onboarding และแนะนำให้ปรึกษาแพทย์ก่อนเริ่มโปรแกรมหากมี (ดู FR12)
13. **Adaptive Symptom Easing** — ผ่อนปรนปริมาณคาร์บ/น้ำตาลในช่วงวันที่ 1-7 หากอาการแย่ลงมาก แทนการหักดิบต่อ (ดู FR13)

### นอกขอบเขต (Out of Scope — MVP)
- การเชื่อมต่อ wearable device / CGM (Continuous Glucose Monitor) — เป็นไปได้ในเฟสถัดไป
- **Native Mobile App (iOS/Android)** — ใช้ Web App (responsive รองรับมือถือผ่านเบราว์เซอร์) เป็นช่องทางเดียวก่อนใน MVP นี้ — อาจพิจารณาขยายในเฟสถัดไป โดย Backend/API/Database ต้องคงหลักการแยกอิสระจาก Frontend เพื่อรองรับได้โดยไม่ต้องรื้อใหม่ (ดูหมายเหตุในหัวข้อ 5) — ยังไม่ตัดสินใจหรือออกแบบรายละเอียดตอนนี้
- LINE Official Account / LINE Messaging API — ไม่ใช้แล้วหลังจาก pivot ไป Web App (ดูเหตุผลในหัวข้อ 1)
- การปรับ phase แบบ dynamic ตามอาการจริงของแต่ละคน
- การคำนวณโภชนาการ/นับแคลอรี่แบบละเอียด (ไม่ใช่จุดขายหลักของ JaiFit)
- ระบบชำระเงิน/สมัครสมาชิกแบบเสียเงิน (จะกำหนดในเฟสถัดไป)
- การให้คำปรึกษาทางการแพทย์โดยตรง (JaiFit ไม่ใช่ผู้เชี่ยวชาญทางการแพทย์ ต้องมี disclaimer ชัดเจน)

## 7. Functional Requirements

### FR1 — เก็บข้อมูลพฤติกรรมการกิน (Behavior Data Collection)
- ระบบต้องให้ user พูดคุย/พิมพ์บอกพฤติกรรมการกินแบบอิสระผ่าน**หน้าแชทบน Web App** (เช่น "เมื่อกี้กินชาไทยไปแก้วนึง") — หลักการเดิมเหมือนตอนใช้ LINE ทุกประการ เปลี่ยนแค่ช่องทาง
- AI ต้องสกัด (extract) ข้อมูลจากบทสนทนาได้อย่างน้อย: **เวลา**, **เมนู/ประเภทอาหาร**, **ความถี่**
- ระบบต้องสะสมข้อมูลเป็น behavior profile ต่อ user แบบต่อเนื่อง และปรับปรุง pattern เมื่อมีข้อมูลใหม่เข้ามา
- กรณีข้อมูลไม่ชัดเจน/กำกวม ระบบต้องถามกลับ (clarifying question) แทนการเดาแบบเงียบๆ

### FR2 — Proactive Nudge Engine
- ระบบต้องส่งข้อความเตือนเชิงรุกก่อนถึงเวลาที่ user มีความเสี่ยงจะกินของต้องห้าม โดยอิงจาก pattern ที่เก็บได้ใน FR1
- ช่องทางส่ง nudge: **Web Push Notification เป็นช่องทางหลัก** (ผ่าน browser ที่ user อนุญาตไว้) และ **Email เป็นช่องทางสำรอง** เมื่อ user ไม่ได้อนุญาต Web Push หรือ browser/อุปกรณ์ไม่รองรับ — เนื้อหาและ logic การตัดสินใจว่าจะส่งเมื่อไหร่ยังคงเหมือนเดิมทุกประการ เปลี่ยนแค่ช่องทางส่งจาก LINE เป็นสองช่องทางนี้
- ข้อความต้องเสนอ **ทางเลือกทดแทนที่เฉพาะเจาะจง** ต่อ user คนนั้น ไม่ใช่คำแนะนำทั่วไป
  - ตัวอย่าง: user มัก กินชาไทยตอนบ่าย 2 → AI ส่งข้อความก่อนบ่าย 2 เสนอ "นมอัลมอนด์" แทน
- ระบบต้องตั้งค่า **default เวลาส่งล่วงหน้าอัตโนมัติที่ 15-30 นาทีก่อนเวลาเสี่ยง** ให้ user ทุกคนตั้งแต่แรกใช้งาน โดยไม่ต้องตั้งค่าเอง และต้องให้ user **ปรับเวลาส่งล่วงหน้าเองได้ภายหลังในหน้าตั้งค่า** (ยืนยันแล้ว — เดิมเป็น open question 10.1)
- Nudge ต้องไม่ถี่จนก่อความรำคาญ — เพดานจำนวนข้อความต่อวันต้อง**ปรับอัตโนมัติตาม phase ปัจจุบันของ user** (phase หนัก เช่น Onset ส่งถี่กว่า, phase คงตัว เช่น Stabilizing/Fat-Adapted ส่งห่างกว่า) ไม่ใช้ตัวเลขตายตัวเดียวตลอดโปรแกรม (ยืนยันแล้ว — เดิมเป็น open question 10.3, ค่า threshold ตัวเลขจริงต่อ phase ยังต้องกำหนดตอน implement)

### FR3 — ติดตาม Phase การเปลี่ยนระบบเผาผลาญ
- ระบบต้องนับวันจากวันเริ่มโปรแกรมของ user แต่ละคน และ map เข้ากับ phase ตาม fixed calendar template (ดูตารางในหัวข้อ 8)
- โทนข้อความและเนื้อหาของ nudge/ข้อความให้กำลังใจต้องปรับตาม phase ปัจจุบันของ user
- ระบบต้องแสดง phase ปัจจุบันของ user ใน dashboard สรุปความคืบหน้า

### FR4 — ข้อความให้กำลังใจ และ Controlled Cheat Meal
- ในช่วง phase ที่ร่างกายอ่อนล้า (เช่น วันที่ 1-7) ระบบต้องส่งข้อความ:
  1. อธิบายว่าอาการที่กำลังเป็น (มือสั่น มึนหัว หงุดหงิด) เป็นเรื่องปกติของกระบวนการเปลี่ยนระบบเผาผลาญ
  2. ให้กำลังใจ ไม่ตัดสิน (non-judgmental tone)
  3. เสนอ "cheat meal ที่ควบคุมได้" เป็นทางเลือกเมื่อ user ใกล้ล้มเลิก — ต้องเป็นเมนู/ปริมาณที่ออกแบบมาเพื่อไม่ทำลายกระบวนการเปลี่ยนระบบเผาผลาญที่กำลังดำเนินอยู่
- ระบบต้องมีกลไก **detect สัญญาณใกล้ล้มเลิกแบบผสม** (ยืนยันแล้ว — เดิมเป็น open question 10.2): (1) **keyword/sentiment detection** จากข้อความที่ user พิมพ์ (เช่น "ทนไม่ไหวแล้ว", "จะเลิกแล้ว") ร่วมกับ (2) **สังเกตพฤติกรรมไม่ตอบสนอง nudge ติดต่อกันหลายครั้ง** เพื่อ trigger ข้อความให้กำลังใจแบบเร่งด่วน — จำนวนครั้ง "ติดต่อกัน" ที่แน่นอนยังต้องกำหนดตอน implement

### FR5 — Dashboard สรุปความคืบหน้า (Simple)
- แสดง phase ปัจจุบันและจำนวนวันที่ผ่านมา
- แสดงสรุป nudge ที่ส่งไปและ user ทำตามคำแนะนำกี่ครั้ง (weekly summary)
- แสดง trend พฤติกรรมเสี่ยงที่ลดลง/เพิ่มขึ้น

### FR6 — เลือกโหมดความเข้มข้นในการปรับพฤติกรรม (Intensity Mode)
- ระบบต้องให้ user เลือกโหมดความเข้มข้นตอน onboarding (ก่อนเริ่มนับวันโปรแกรม) ระหว่าง 2 โหมด:
  1. **โหมดหักดิบ (fast-track)** — เข้มงวด มุ่งพา user ผ่านช่วง 7-10 วันแรกให้ได้ก่อน (nudge ถี่กว่า, เนื้อหาเน้นวินัย/ผลลัพธ์เร็ว) แล้วจึงเริ่มเสนอทางเลือกทดแทนอาหารแบบเป็นระบบหลังจากผ่านไปแล้ว 1-2 สัปดาห์
  2. **โหมดค่อยเป็นค่อยไป (gradual)** — ให้คำแนะนำและให้กำลังใจแบบช้าๆ ตลอดเส้นทาง ตั้งแต่วันแรก ไม่เร่งรัด
- User ต้องสามารถดูโหมดที่เลือกไว้ได้ และ**เปลี่ยนโหมดภายหลังได้ตลอดเวลา ไม่จำกัดจำนวนครั้ง** (ยืนยันแล้ว — เดิมเป็น open question 10.6) แต่ระบบ**ต้องอธิบายผลลัพธ์ที่จะได้รับให้ user เข้าใจก่อนเปลี่ยนโหมดทุกครั้ง** (เช่น หากเปลี่ยนเป็นโหมดค่อยเป็นค่อยไป ผลลัพธ์จะช้าลงแต่ยั่งยืนกว่า โดยอ้างอิงหลักการว่า "อ้วนก็ไม่ได้อ้วนในวันสองวัน การลดก็ไม่ควรคาดหวังผลในวันสองวันเช่นกัน")
- โหมดที่เลือกต้องส่งผลต่อ: ความถี่ nudge, จังหวะที่เริ่มเสนอทางเลือกทดแทน (FR2), และโทนเนื้อหาที่ Content & Tone Engine เลือกใช้ (FR3, FR4)

### FR7 — ความหลากหลายของข้อความจูงใจ (Message Variety)
- ระบบต้อง**ไม่ส่งคำแนะนำ/เมนูทดแทน/ข้อความให้กำลังใจแบบเดิมซ้ำๆ ติดต่อกันหลายวัน** (เช่น ห้ามแนะนำเมนูเดียวกันซ้ำ 7-10 วันติดโดยไม่ปรับ) เพราะทำให้ user เบื่อและเลิกกลางทาง
- ระบบต้องมีกลไกหมุนเวียน (rotate) รูปแบบการสื่อสาร**แบบผสม** (ยืนยันแล้ว — เดิมเป็น open question 10.7): มี **content library** เป็นฐานข้อความที่เตรียมไว้ล่วงหน้า แล้วให้ **AI ปรับถ้อยคำ/มุมมองให้เข้ากับ context ของ user แต่ละคน** เช่น สลับเมนูทดแทนที่เสนอ, สลับมุมมอง/น้ำเสียงของข้อความให้กำลังใจ, สลับรูปแบบการตั้งคำถามชวนคุย
- ระบบต้องจดจำว่าเคยส่งข้อความ/เมนูใดให้ user คนนั้นไปแล้วเมื่อไหร่ เพื่อหลีกเลี่ยงการส่งซ้ำในช่วงเวลาใกล้กัน

### FR8 — เตือนล่วงหน้าเรื่องอาการ/สถานการณ์ไม่พึงประสงค์ (Proactive Downside Warning)
- ระบบต้องสื่อสารทั้งด้านบวก **และ** เตือนล่วงหน้าถึงอาการ/สถานการณ์แย่ๆ ที่มีโอกาสเกิดขึ้นในช่วง phase นั้นๆ (เช่น "ช่วงนี้อาจมีมือสั่น มึนหัวได้ ถ้าเกิดขึ้นให้ลองวิธีนี้แก้") เพื่อไม่ให้ user ตกใจเมื่อเจอสถานการณ์จริงที่ไม่มีใครเตือนมาก่อน
- เนื้อหาการเตือนล่วงหน้าใช้**สมมติฐานเบื้องต้นจากประสบการณ์ผู้ก่อตั้งไปก่อนใน MVP** แล้วปรับตาม feedback จริงภายหลัง (ยืนยันแล้ว — เดิมเป็น open question 10.8 — เช่นเดียวกับแนวทางของตาราง phase ในหัวข้อ 8)
- ข้อความเตือนล่วงหน้าต้องมาพร้อม**วิธีรับมือที่ทำได้จริงทันที** เสมอ ไม่ใช่แจ้งอาการเฉยๆ โดยไม่มีทางออก
- เนื้อหาการเตือนล่วงหน้าต้องอ้างอิงกับ phase ปัจจุบันและ intensity mode ของ user (เช่น fast-track อาจมีอาการรุนแรงกว่าและถี่กว่า gradual ในช่วงวันแรกๆ)

### FR9 — Reward System (ปลดล็อก Cheat Meal / Cheat Day ตาม Milestone)
- ระบบต้องนับ **streak วันต่อเนื่อง** ที่ user ทำตามแผน (ไม่หลุดกินอิสระ/ไม่ล้มเลิก) นับจากวันเริ่มโปรแกรมหรือวันล่าสุดที่ streak ขาด
- เมื่อ streak ครบ **7 วันต่อเนื่อง** ระบบต้องปลดล็อกสิทธิ์ **cheat meal 1 มื้อที่ยังควบคุมได้** (ใช้เมนูจาก `CheatMealOption` เดิม ไม่ทำลายกระบวนการเปลี่ยนระบบเผาผลาญ)
- เมื่อ streak ครบ **30 วันต่อเนื่อง** ระบบต้องปลดล็อกสิทธิ์ **cheat day เต็มวัน**
- ระบบต้องแจ้ง user เมื่อปลดล็อกรางวัลสำเร็จ ด้วยข้อความฉลองความสำเร็จ (เชื่อมกับ FR7 เรื่องความหลากหลายของข้อความ)
- กรณี streak ขาด (user หลุดกินอิสระ/ล้มเลิกกลางทาง) ระบบต้องนับ streak ใหม่แบบไม่ตัดสิน (non-judgmental) สอดคล้องกับโทนใน FR4 — **ต้องให้ streak "พัก" ได้ 1 วันโดยไม่ถูกตัด (grace day)** ก่อนจะรีเซ็ตจริง เพื่อผ่อนปรนและลดความรู้สึกผิดของ user (ยืนยันแล้ว — เดิมเป็น open question 10.9)

### FR10 — Motivation Profiling (เก็บข้อมูลแรงจูงใจของ user)
- ระบบต้องถาม user เกี่ยวกับ **แรงจูงใจ/สาเหตุที่อยากลดน้ำหนักเปลี่ยนชีวิต** ตอน onboarding (ก่อนหรือพร้อมกับการเลือก intensity mode ใน FR6) ผ่านบทสนทนาอิสระเหมือนกับ FR1 ไม่ใช่แบบฟอร์มเลือกตัวเลือกตายตัว
- ระบบต้องจัดกลุ่มแรงจูงใจที่สกัดได้เป็นระดับความเข้มแข็งทางใจ โดยใช้ **4 กลุ่มจากประสบการณ์ผู้ก่อตั้งเป็นฐาน** (ยืนยันแล้ว — เดิมเป็น open question 10.10) **แต่ให้ AI มีความยืดหยุ่นในการประเมินระดับความเข้มแข็งจากบทสนทนาจริงได้ ไม่ยึดติดตายตัว 100%** (เช่น ปรับ strength_level ขึ้น/ลงจากฐานกลุ่มได้ถ้าเนื้อหาบทสนทนาแสดงสัญญาณที่ชัดเจนกว่าการจัดกลุ่มแบบตายตัว):
  1. **ถูกคนอื่นบังคับ/หมอสั่ง** — มักมีความเข้มแข็งทางใจ**อ่อนแอกว่า**
  2. **กลัวจากเหตุการณ์ภายนอก** (เช่น ข่าวคนดังป่วย) — ความเข้มแข็งทางใจ**ปานกลาง**
  3. **อยากทำเพื่อคนที่รักหรือสิ่งที่มีความหมาย** — ความเข้มแข็งทางใจสูง
  4. **ตระหนักด้วยตัวเองจากสภาพร่างกาย** — ความเข้มแข็งทางใจ**สูงกว่า**
- AI ต้องใช้ระดับความเข้มแข็งทางใจนี้ปรับ **ความหนักเบาของโทนการพูดคุยและความถี่ในการให้กำลังใจ** — เช่น user ที่แรงจูงใจอ่อนกว่าอาจต้องการการเตือน/ให้กำลังใจถี่กว่า ปรับเสริมกับความถี่ที่กำหนดไว้แล้วตาม phase (FR3) และ intensity mode (FR6)
- AI ต้องสามารถ **โยงข้อความให้กำลังใจกลับไปหาแรงจูงใจเดิม** ของ user ได้ (เช่น เตือนถึงเป้าหมายที่อยากอยู่กับคนที่รักนานๆ) เมื่อส่งข้อความให้กำลังใจ (FR4) หรือข้อความฉลองปลดล็อกรางวัล (FR9)
- กรณีข้อมูลแรงจูงใจที่ user เล่าไม่ชัดเจน/จัดกลุ่มไม่ได้ ระบบต้องถามกลับเพื่อความชัดเจน (สอดคล้องกับหลักการเดียวกับ FR1) แทนการเดา หรือจัดเป็นกลุ่ม "ไม่ระบุ" หากยังกำกวมอยู่
- **การถามทบทวนแรงจูงใจซ้ำหลัง onboarding** (ยืนยันแล้ว — เดิมเป็น open question 10.11) ขึ้นกับกลุ่มความเข้มแข็งทางใจของ user: user ที่มีแรงจูงใจกลุ่ม**เข้มแข็ง** (เพื่อคนที่รัก, ตระหนักด้วยตัวเอง) ให้ใช้ค่าที่เก็บไว้ตอน onboarding **ตลอดโปรแกรมโดยไม่ถามซ้ำ** — ส่วน user ที่มีแรงจูงใจกลุ่ม**อ่อนกว่า** (ถูกบังคับ, กลัวจากข่าว) ให้ AI **ถามทบทวนเป็นระยะ** โดยจังหวะที่เหมาะสมคือ**หลังจาก user ได้รับ reward จาก Reward System (FR9)** เพราะเป็นจุดที่ user มักรู้สึกถึงความสำเร็จอยู่แล้ว

### FR11 — สมัครสมาชิก/เข้าสู่ระบบ (Account Signup & Login)
- ระบบต้องให้ user สมัครสมาชิก/เข้าสู่ระบบด้วย **2 วิธีให้เลือกเอง** (ยืนยันแล้ว — เดิมเป็น open question 10.13): **Google Sign-In (OAuth)** หรือ **Email/Password** แบบดั้งเดิม เพื่อระบุตัวตนบน Web App แทนการอิง LINE user ID โดยอัตโนมัติแบบเดิม
- กลไก authentication/session หลักของระบบใช้ **JWT Token** (เหมาะกับสถาปัตยกรรม React + Node.js ที่แยก Frontend/Backend ชัดเจน) — token ต้องแนบมากับทุก request หลัง login/signup เพื่อคงสถานะการเข้าสู่ระบบไว้ ไม่ต้อง login ซ้ำทุกครั้งที่เปิดเว็บ (ภายในอายุ token ที่กำหนด)
- ระบบต้องขอสิทธิ์ **Web Push Notification** จาก browser ของ user ตอน onboarding (หลัง signup) เพื่อให้ FR2 ส่ง nudge ได้ — หาก user ไม่อนุญาต ระบบต้องแจ้งว่าจะใช้ Email แทนเป็นช่องทางหลัก
- กรณีสมัคร/เข้าสู่ระบบด้วย **Email/Password** รหัสผ่านต้องถูกเก็บแบบเข้ารหัส (hashed) ไม่เก็บเป็น plain text — เป็นข้อกำหนดความปลอดภัยขั้นต่ำที่จำเป็นเมื่อมีระบบบัญชีผู้ใช้จริง
- กรณีสมัคร/เข้าสู่ระบบด้วย **Google Sign-In** ระบบไม่ต้องเก็บรหัสผ่านของ user เอง แต่ต้องเก็บข้อมูลอ้างอิงบัญชี Google (เช่น Google account ID) เพื่อผูกกับบัญชี JaiFit ของ user คนนั้น

### FR12 — Chronic Condition Screening (คัดกรองโรคประจำตัว)
- ระบบต้องถาม user ตอน onboarding (ก่อนเริ่มนับวันโปรแกรม เช่น พร้อมกับหรือหลัง Motivation Profiling ใน FR10) ว่ามี**โรคประจำตัว**หรือไม่ (เช่น ความดันโลหิตสูง, เบาหวาน) ผ่านบทสนทนาอิสระหรือคำถามปิด (ทีมเทคนิคเลือก UX ที่เหมาะสมได้)
- หาก user ระบุว่ามีโรคประจำตัว ระบบต้อง**แนะนำให้ปรึกษาแพทย์ก่อนเริ่มโปรแกรม** ด้วย disclaimer ที่ชัดเจน (สอดคล้องกับ NFR Disclaimer ทางการแพทย์ในหัวข้อ 9) — ใน MVP ระบบยังคงให้ user เริ่มโปรแกรมต่อได้เองหลังรับทราบคำแนะนำ (ไม่ได้ block การใช้งาน เพราะ JaiFit ไม่ใช่ระบบให้คำปรึกษาทางการแพทย์โดยตรง)
- หาก user ระบุว่าไม่มีโรคประจำตัว (อยู่ในกลุ่มเสี่ยงจากน้ำหนัก/Body Fat เท่านั้น) ระบบให้เริ่มโปรแกรมได้ตามปกติโดยไม่ต้องแสดง disclaimer เพิ่มเติม
- ผลการคัดกรองนี้เป็น input ให้ FR13 (Adaptive Symptom Easing) ใช้ประกอบการตัดสินใจร่วมกับสัญญาณอาการที่ user รายงาน

### FR13 — Adaptive Symptom Easing (ผ่อนปรนตามอาการช่วงวันที่ 1-7)
- ในช่วงวันที่ 1-7 ของโปรแกรม (phase Onset/Adaptation) หาก user รายงานผ่านบทสนทนาอิสระ (กลไกเดียวกับ FR1) ว่าอาการ**แย่ลงมาก** (เช่น เวียนหัวรุนแรง อ่อนเพลียจนทำกิจวัตรไม่ได้ ไม่ใช่แค่มือสั่น/หงุดหงิดทั่วไปตามที่ FR4 อธิบายว่าเป็นเรื่องปกติ) ระบบต้อง**ผ่อนปรนปริมาณคาร์บ/น้ำตาลที่แนะนำ** ให้ user แทนการหักดิบต่อตาม intensity mode เดิมที่เลือกไว้ (FR6)
- การผ่อนปรนนี้ใช้ได้กับ user ทุกกลุ่ม (ทั้งกลุ่มที่มีโรคประจำตัวและกลุ่มเสี่ยงที่ไม่มี — ดู FR12) แต่มีความสำคัญเป็นพิเศษกับ user ที่มีโรคประจำตัว
- ระบบต้องสื่อสารกับ user อย่างชัดเจนว่า การผ่อนปรนนี้ทำให้**น้ำหนักลดช้าลงกว่าที่คาดไว้ แต่ยังคงลดในระดับที่น่าพอใจและปลอดภัยกว่า** เพื่อไม่ให้ user รู้สึกว่าล้มเหลว (สอดคล้องกับโทน non-judgmental ของ FR4)
- Phase timeline (fixed calendar-based ตาม FR3) **ไม่เปลี่ยนแปลง**จากการผ่อนปรนนี้ — สิ่งที่เปลี่ยนคือเนื้อหา/ปริมาณคาร์บที่แนะนำในข้อความเท่านั้น ไม่ใช่การเลื่อน phase

## 8. Business Rules — Phase Template (สมมติฐานเบื้องต้น)

> ⚠️ ตารางนี้เป็น **สมมติฐานเบื้องต้นที่ต้องให้ผู้เชี่ยวชาญด้านโภชนาการ/แพทย์ตรวจสอบ** ก่อนใช้งานจริง เพราะเป็นข้อมูลที่กระทบสุขภาพ user โดยตรง — ยืนยันแล้ว (เดิมเป็น open question 10.4) ว่า MVP นี้ใช้สมมติฐานเบื้องต้นไปก่อน แล้วปรับตาม feedback จริง/การ validate จากผู้เชี่ยวชาญภายหลัง

| Phase | ช่วงวัน | ลักษณะอาการ | โทนข้อความที่ต้องการ |
|---|---|---|---|
| Onset (เริ่มถอนน้ำตาล) | วันที่ 1-3 | อาการหนักสุด: มือสั่น มึนหัว หงุดหงิด อยากอาหารรุนแรง | ให้กำลังใจสูงสุด, เน้นอธิบายว่าปกติ, nudge ถี่และเสนอทางเลือกทดแทนทันที |
| Adaptation (ปรับตัว) | วันที่ 4-7 | อาการเริ่มลดลงแต่ยังอ่อนเพลีย | ให้กำลังใจต่อเนื่อง, ลดความถี่ nudge ลงเล็กน้อย, เริ่มเสนอ cheat meal แบบควบคุมได้หากจำเป็น |
| Stabilizing (คงตัว) | วันที่ 8-14 | ร่างกายเริ่มปรับเข้าสู่การเผาผลาญไขมัน | โทนให้กำลังใจแบบฉลองความสำเร็จ, nudge เชิงป้องกันตามปกติ |
| Fat-Adapted (ปรับระบบสำเร็จ) | วันที่ 15 เป็นต้นไป | อาการถอนน้ำตาลหายเป็นส่วนใหญ่ | โทนสนับสนุนระยะยาว, เน้นรักษาพฤติกรรม |

> ตารางนี้เป็นฐานร่วมของทั้งสองโหมด — **โหมดหักดิบ (fast-track)** ใช้จังหวะ nudge ที่ถี่กว่าและเลื่อนการเสนอทางเลือกทดแทนแบบเป็นระบบไปหลัง 1-2 สัปดาห์ (ตรงกับช่วง Stabilizing) ตาม FR6, ส่วน **โหมดค่อยเป็นค่อยไป (gradual)** เสนอทางเลือกทดแทนได้ตั้งแต่ phase Onset ตามปกติของ FR2

### 8.1 การแยกตามกลุ่มผู้ใช้ (ยืนยันแล้ว — เดิมเป็นส่วนหนึ่งของ open question 10.4)

ตารางข้างต้นใช้ร่วมกันเป็นฐาน แต่ระบบต้องแยก flow ตามกลุ่มผู้ใช้ที่คัดกรองได้จาก FR12 (Chronic Condition Screening):

| กลุ่มผู้ใช้ | เงื่อนไข | สิ่งที่ระบบต้องทำเพิ่ม |
|---|---|---|
| กลุ่มมีโรคประจำตัว | ระบุว่ามีโรคประจำตัว (ความดัน, เบาหวาน ฯลฯ) ตอน onboarding | ต้องได้รับคำแนะนำให้**ปรึกษาแพทย์ก่อนเริ่มโปรแกรม** ด้วย disclaimer ชัดเจน (FR12) ก่อนเข้าสู่ phase Onset |
| กลุ่มเสี่ยง (ไม่มีโรคประจำตัว) | น้ำหนักเกิน/Body Fat สูงตาม Target Users ในหัวข้อ 3 แต่ไม่มีโรคประจำตัว | เริ่มโปรแกรมได้เองตามตาราง phase ปกติโดยไม่ต้องมี disclaimer เพิ่มเติม |

**กติกาผ่อนปรนช่วงวันที่ 1-7 (Adaptive Symptom Easing, FR13):** หาก user กลุ่มใดกลุ่มหนึ่งข้างต้นรายงานว่าอาการแย่ลงมากในช่วง Onset/Adaptation ระบบต้องผ่อนปรนปริมาณคาร์บ/น้ำตาลให้ไม่ตึงเกินไปแทนการหักดิบต่อตาม intensity mode เดิม — ผลลัพธ์คือน้ำหนักลดช้าลงกว่าที่คาดแต่ยังลดในระดับที่น่าพอใจและปลอดภัยกว่า Phase timeline ในตารางข้างต้นไม่เปลี่ยนแปลงจากกติกานี้ (ดู FR13)

## 9. Non-Functional Requirements

- **ความเป็นส่วนตัวของข้อมูลสุขภาพ**: ข้อมูลพฤติกรรมการกิน/น้ำหนัก/Body Fat ถือเป็นข้อมูลส่วนบุคคลที่มีความอ่อนไหวภายใต้ PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล) ต้องขอ consent ชัดเจนก่อนเก็บข้อมูล และแจ้งวัตถุประสงค์การใช้
- **Disclaimer ทางการแพทย์**: ต้องระบุชัดเจนว่า JaiFit ไม่ใช่คำแนะนำทางการแพทย์ และควรปรึกษาแพทย์ก่อนเริ่มโปรแกรมลดน้ำหนักที่มีความเสี่ยงสูง (เช่น มีโรคประจำตัว)
- **ความแม่นยำของเวลา nudge**: ระบบต้องส่งข้อความให้ทันเวลาก่อนช่วงเสี่ยงจริง (ไม่ใช่ real-time ระดับวินาที แต่ต้องอยู่ใน window ที่กำหนดไว้ใน FR2)
- **Availability**: ต้องพึ่งพา Web Push API/บริการ Email ได้อย่างเสถียร (สองช่องทางตาม FR2) รวมถึง availability ของ web server/hosting ของ JaiFit เองที่ deploy จริง เนื่องจากไม่มี platform กลาง (เช่น LINE) มารองรับความเสถียรของการส่งข้อความให้อีกต่อไป
- **ความปลอดภัยของบัญชีผู้ใช้**: รหัสผ่านต้องเก็บแบบ hashed, การเชื่อมต่อระหว่าง Frontend-Backend ต้องผ่าน HTTPS, และ session/token ต้องมีอายุ (expiry) ที่เหมาะสม — จำเป็นเพราะเปลี่ยนจากอิง LINE identity มาเป็นระบบบัญชีของ JaiFit เอง (ดู FR11)
- **Deploy ใช้งานได้จริง**: ต้อง deploy Frontend, Backend, และ Database ให้ใช้งานได้จริงผ่านอินเทอร์เน็ต ไม่ใช่รันบนเครื่อง local เท่านั้น — เป็นข้อกำหนดของหลักสูตร ADT-RAISE

## 10. Open Questions — สถานะหลังปิดรอบ 4 (2026-08-29)

12 จาก 13 ข้อด้านล่างถูก**ปิดแล้ว**ด้วยการตัดสินใจที่ยืนยันในหัวข้อ 5 (ดู [[../../05-log/20260829-log|log 2026-08-29]] สำหรับสรุปเหตุผล) เหลือเฉพาะ **10.5** ที่ยังเปิดอยู่เพราะรอข้อมูล baseline เพิ่มเติม

### ~~10.1 เวลาที่ส่ง nudge ล่วงหน้าเท่าไหร่ถึงจะพอดี~~ — ปิดแล้ว
**ตัดสินใจ:** ตั้งค่า default อัตโนมัติ 15-30 นาทีก่อนเวลาเสี่ยงให้ทุก user ตั้งแต่แรก และให้ user ปรับเวลาเองได้ภายหลังในหน้าตั้งค่า — ดู FR2

### ~~10.2 วิธี detect ว่า user "ใกล้ล้มเลิก"~~ — ปิดแล้ว
**ตัดสินใจ:** ใช้แบบผสม keyword/sentiment detection จากข้อความที่พิมพ์ ร่วมกับสังเกตพฤติกรรมไม่ตอบสนอง nudge ติดต่อกันหลายครั้ง — ดู FR4

### ~~10.3 เพดานจำนวน nudge ต่อวัน~~ — ปิดแล้ว
**ตัดสินใจ:** ปรับอัตโนมัติตาม phase (phase หนักส่งถี่กว่า, phase คงตัวส่งห่างกว่า) ไม่ใช้ตัวเลขตายตัว — ดู FR2

### ~~10.4 ตาราง phase (หัวข้อ 8) ควรอ้างอิงจากอะไร~~ — ปิดแล้ว
**ตัดสินใจ:** ใช้สมมติฐานในเอกสารนี้ไปก่อน (MVP) แล้วปรับตาม feedback จริงภายหลัง **พร้อมแยก flow ตามกลุ่มผู้ใช้** — กลุ่มมีโรคประจำตัวต้องปรึกษาแพทย์ก่อนเริ่ม (FR12), กลุ่มเสี่ยงที่ไม่มีโรคประจำตัวเริ่มได้เอง, และผ่อนปรนคาร์บ/น้ำตาลถ้าอาการแย่ลงมากในวันที่ 1-7 (FR13) — ดูหัวข้อ 8.1

### 10.5 Target metric ตัวเลขจริงในหัวข้อ 4 — ยังเปิดอยู่
- ยังไม่มีข้อมูล baseline (drop-out rate ปัจจุบันโดยไม่มีระบบ) — ต้องสอบถามหรือประมาณการร่วมกับผู้ใช้ก่อนตั้งเป้าใน [[../02-plan/index|02-plan]] — **ไม่ได้ปิดในรอบนี้**

### ~~10.6 ความถี่ที่อนุญาตให้ user เปลี่ยนโหมดความเข้มข้น (FR6)~~ — ปิดแล้ว
**ตัดสินใจ:** เปลี่ยนได้ตลอดเวลา ไม่จำกัดจำนวนครั้ง แต่ระบบต้องอธิบายผลลัพธ์ที่จะได้รับให้ user เข้าใจก่อนเปลี่ยนทุกครั้ง — ดู FR6

### ~~10.7 กลไกหมุนเวียนข้อความ (FR7)~~ — ปิดแล้ว
**ตัดสินใจ:** ใช้แบบผสม — content library เป็นฐาน แล้วให้ AI ปรับถ้อยคำ/มุมมองให้เข้ากับ context ของ user แต่ละคน — ดู FR7

### ~~10.8 เนื้อหาการเตือนล่วงหน้า (FR8) ควรมาจากไหน~~ — ปิดแล้ว
**ตัดสินใจ:** ใช้สมมติฐานเบื้องต้นจากประสบการณ์ผู้ก่อตั้งไปก่อนใน MVP แล้วปรับตาม feedback จริงภายหลัง — ดู FR8

### ~~10.9 กติกาการนับ/รีเซ็ต streak ของ Reward System (FR9)~~ — ปิดแล้ว
**ตัดสินใจ:** ให้ streak พักได้ 1 วันโดยไม่ถูกตัด (grace day) ก่อนจะตัดจริง — ดู FR9

### ~~10.10 การจัดกลุ่มระดับความเข้มแข็งทางใจจากแรงจูงใจ (FR10)~~ — ปิดแล้ว
**ตัดสินใจ:** ใช้ 4 กลุ่มจากประสบการณ์ผู้ก่อตั้งเป็นฐาน แต่ให้ AI มีความยืดหยุ่นในการประเมินระดับความเข้มแข็งจากบทสนทนาจริงได้ ไม่ยึดติดตายตัว 100% — ดู FR10

### ~~10.11 ควรถาม/ทบทวนแรงจูงใจของ user ซ้ำอีกหรือไม่หลัง onboarding~~ — ปิดแล้ว
**ตัดสินใจ:** กลุ่มแรงจูงใจเข้มแข็ง (เพื่อคนที่รัก, ตระหนักด้วยตัวเอง) ใช้ค่าที่เก็บตอน onboarding ตลอดโปรแกรมไม่ถามซ้ำ — กลุ่มแรงจูงใจอ่อนกว่า (ถูกบังคับ, กลัวจากข่าว) ให้ AI ถามทบทวนเป็นระยะ โดยจังหวะที่เหมาะสมคือหลังจาก user ได้รับ reward จาก Reward System (FR9) — ดู FR10

### ~~10.12 นโยบาย fallback เมื่อ user ไม่อนุญาต Web Push (FR2, FR11)~~ — ปิดแล้ว
**ตัดสินใจ:** ตัดช่องทาง LINE ออก ใช้เฉพาะ Web Push Notification เป็นช่องทางหลักและ Email เป็นช่องทางสำรองตามที่ตัดสินใจไว้เดิมใน FR2 ไม่เพิ่มช่องทางอื่น

### ~~10.13 กลไก authentication/session ที่แน่นอน (FR11)~~ — ปิดแล้ว
**ตัดสินใจ:** ใช้ JWT Token เป็นกลไกหลัก และรองรับ 2 วิธีสมัคร/เข้าสู่ระบบ: Google Sign-In (OAuth) และ Email/Password แบบดั้งเดิม ให้ user เลือกได้เอง — ดู FR11
