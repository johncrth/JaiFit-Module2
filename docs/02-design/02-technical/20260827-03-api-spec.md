## Authentication (ใช้ร่วมกันทุก operation ด้านล่าง)

- ทุก operation **ต้องผ่าน authentication ด้วย JWT Token** (ยืนยันแล้ว — เดิม open question 10.13) ที่ส่งใน header `Authorization: Bearer <token>` **ยกเว้น** `POST /api/auth/signup`, `POST /api/auth/login`, และ `POST /api/auth/google` ที่ต้องเปิดให้เรียกได้โดยไม่มี token (เป็นจุดเริ่มต้นของการยืนยันตัวตน)
- Operation ที่ระบุ `user_id` เป็น input ในเอกสารนี้ ในทางปฏิบัติควรดึงจาก token ที่ยืนยันตัวตนแล้ว (ไม่รับ `user_id` จาก client โดยตรง) ยกเว้นกรณี internal/scheduler-triggered operation (B1, D1, G1, G2, I2, C2) ที่เรียกจาก background process ภายในระบบ ไม่ใช่ user-facing request โดยตรง — operation กลุ่มนี้ควรมีกลไกยืนยันตัวตนแบบ service-to-service แยกต่างหาก (เช่น internal shared secret) ไม่ใช่ user token
- Error case ร่วม: ไม่มี token / token หมดอายุ / token ไม่ถูกต้อง → คืนสถานะ unauthorized สำหรับทุก operation ที่ต้อง authentication (ไม่ระบุซ้ำในแต่ละ operation ด้านล่างเพื่อความกระชับ)

## กลุ่ม Auth — สมัครสมาชิก/เข้าสู่ระบบ (FR11)

### Auth1. Signup
- **HTTP:** `POST /api/auth/signup`
- **วัตถุประสงค์:** สร้างบัญชีผู้ใช้ใหม่ด้วยอีเมล + รหัสผ่าน แทนการอิง LINE user ID โดยอัตโนมัติแบบเดิม
- **Authentication:** ไม่ต้องผ่าน (public endpoint)
- **Input:** `email`, `password`
- **Output:** `user_id`, token/session (รูปแบบขึ้นกับแนวทางที่เลือกจาก open question 10.13)
- **Error case:** `email` ซ้ำกับบัญชีที่มีอยู่แล้ว → ปฏิเสธคำขอพร้อมแจ้งเหตุผล; รหัสผ่านไม่ผ่านเกณฑ์ความปลอดภัยขั้นต่ำ (ความยาว/ความซับซ้อน — เกณฑ์จริงยังไม่กำหนด ดูสมมติฐาน) → ปฏิเสธคำขอ; รหัสผ่านต้องถูก hash ก่อนบันทึกลง `User.password_hash` เสมอ ห้ามเก็บ plain text
- **อ้างอิง:** FR11

### Auth2. Login
- **HTTP:** `POST /api/auth/login`
- **วัตถุประสงค์:** ยืนยันตัวตนด้วยอีเมล + รหัสผ่าน แล้วออก token/session สำหรับใช้เรียก operation อื่นต่อ
- **Authentication:** ไม่ต้องผ่าน (public endpoint)
- **Input:** `email`, `password`
- **Output:** token/session, ข้อมูลผู้ใช้พื้นฐาน (`user_id`, `email`)
- **Error case:** อีเมล/รหัสผ่านไม่ถูกต้อง → ปฏิเสธคำขอแบบ generic error (ไม่ระบุว่าอีเมลหรือรหัสผ่านผิด เพื่อลดความเสี่ยง user enumeration)
- **อ้างอิง:** FR11

### Auth1b. Google Sign-In
- **HTTP:** `POST /api/auth/google`
- **วัตถุประสงค์:** สมัครสมาชิก **หรือ** เข้าสู่ระบบด้วย Google Sign-In (OAuth) — endpoint เดียวรองรับทั้งสองกรณี: ถ้า `google_id` ยังไม่มีบัญชี ให้สร้างบัญชีใหม่ (`auth_provider = google`), ถ้ามีอยู่แล้วให้ login เข้าบัญชีเดิม
- **Authentication:** ไม่ต้องผ่าน (public endpoint)
- **Input:** `google_id_token` (ID token ที่ได้จาก Google Sign-In SDK ฝั่ง frontend)
- **Output:** `user_id`, JWT token, `is_new_user` (boolean — ใช้ frontend ตัดสินใจว่าจะพา user เข้า onboarding หรือหน้าหลัก)
- **Error case:** `google_id_token` ไม่ถูกต้อง/verify กับ Google ไม่ผ่าน → ปฏิเสธคำขอ; อีเมลจาก Google ตรงกับบัญชีที่สมัครด้วย `auth_provider = email_password` อยู่แล้ว → ปฏิเสธคำขอพร้อมแจ้งให้ login ด้วยอีเมล/รหัสผ่านแทน (ไม่ auto-merge บัญชีใน MVP นี้)
- **อ้างอิง:** FR11

### Auth3. Get Current User
- **HTTP:** `GET /api/auth/me`
- **วัตถุประสงค์:** ดึงข้อมูลบัญชีของผู้ใช้ที่ login อยู่ปัจจุบัน (ใช้ตอนโหลดหน้าเว็บเพื่อตรวจสอบ session ว่ายังใช้ได้ และแสดงข้อมูลโปรไฟล์)
- **Input:** — (อ่านจาก token)
- **Output:** `user_id`, `email`, `auth_provider`, `program_start_date`, `intensity_mode`, `has_chronic_condition`, `created_at` (ไม่คืน `password_hash`)
- **Error case:** token ไม่ถูกต้อง/หมดอายุ → unauthorized
- **อ้างอิง:** FR11

### Auth4. Register Push Subscription
- **HTTP:** `POST /api/notifications/push-subscription`
- **วัตถุประสงค์:** บันทึก Web Push subscription ที่ browser สร้างให้หลังจาก user อนุญาตสิทธิ์ Web Push Notification (เรียกหลัง signup ตอน onboarding ตาม FR11) เพื่อให้ B2/D2 ส่ง nudge/ข้อความให้กำลังใจผ่าน Web Push ได้
- **Input:** `endpoint`, `p256dh_key`, `auth_key`, `user_agent` (optional)
- **Output:** `push_subscription_id`
- **Error case:** `endpoint` ซ้ำกับ subscription ที่มีอยู่แล้ว (เช่น ลงทะเบียนซ้ำจาก browser เดิม) → อัปเดต record เดิมแทนการสร้างซ้ำ (upsert ตาม `endpoint`) และตั้ง `is_active = true`
- **อ้างอิง:** FR11, FR2

### Auth5. Remove Push Subscription
- **HTTP:** `DELETE /api/notifications/push-subscription/{push_subscription_id}`
- **วัตถุประสงค์:** ยกเลิก Web Push subscription (เช่น user ปิด permission ทีหลัง หรือ push service แจ้งว่า endpoint หมดอายุถาวร — HTTP 410 Gone)
- **Input:** `push_subscription_id` (path parameter)
- **Output:** สถานะสำเร็จ
- **Error case:** `push_subscription_id` ไม่พบ หรือไม่ใช่ของ user ที่ login อยู่ → ปฏิเสธคำขอ
- **อ้างอิง:** FR11, FR2

## กลุ่ม A — เก็บข้อมูลพฤติกรรมการกิน (FR1)

### A1. Submit Conversation Message
- **HTTP:** `POST /api/behavior/messages`
- **วัตถุประสงค์:** รับข้อความอิสระที่ user พิมพ์เข้ามา ส่งต่อให้ Behavior Profile Engine ประมวลผล
- **Input:** `message_text`, `sent_at` (`user_id` อ่านจาก token)
- **Output:** `message_id`, และอย่างใดอย่างหนึ่งต่อไปนี้:
  - `extracted_pattern` (ถ้าสกัดได้ชัดเจน — อ้างอิง `BehaviorPattern`)
  - `clarifying_question` (ถ้าข้อมูลกำกวม — `needs_clarification = true` ใน `ConversationMessage`)
- **Error case:** ข้อความว่าง/ไม่มีเนื้อหาที่เกี่ยวข้องกับพฤติกรรมการกิน → บันทึกเป็น log ปกติโดยไม่สร้าง pattern ใหม่
- **อ้างอิง:** FR1 (F1, F2, F3)

### A2. Get Behavior Profile
- **HTTP:** `GET /api/behavior/patterns`
- **วัตถุประสงค์:** ดึง pattern ทั้งหมดของ user (ใช้โดย Nudge Scheduler และ Dashboard Service)
- **Input:** — (`user_id` อ่านจาก token)
- **Output:** รายการ `BehaviorPattern` (time_window, menu_or_category, frequency_count, confidence_level)
- **อ้างอิง:** FR1 (F4), FR2

## กลุ่ม B — Proactive Nudge Engine (FR2)

### B1. Evaluate Upcoming Risk Windows
- **HTTP:** `POST /api/internal/nudges/evaluate-risk-windows`
- **วัตถุประสงค์:** ประเมิน pattern ของ user เทียบกับเวลาปัจจุบัน เพื่อหาว่ามีช่วงเวลาเสี่ยงที่กำลังจะถึงหรือไม่ (เรียกโดย Nudge Scheduler ตามรอบ — internal/scheduler-triggered ไม่ใช่ user-facing request) ความถี่/เพดาน nudge ที่ประเมินได้ต้องปรับตาม `User.intensity_mode` ปัจจุบัน (fast-track = ถี่กว่าในช่วง 7-10 วันแรก, gradual = สม่ำเสมอตลอด) **และต้องปรับเพดานอัตโนมัติตาม phase ปัจจุบันของ user** (phase หนักเช่น Onset ส่งถี่กว่า, phase คงตัวเช่น Stabilizing/Fat-Adapted ส่งห่างกว่า — ยืนยันแล้ว เดิม open question 10.3) และใช้ default เวลาส่งล่วงหน้า 15-30 นาทีก่อนเวลาเสี่ยง เว้นแต่ user ปรับค่าไว้เองผ่าน B4 (ยืนยันแล้ว เดิม open question 10.1)
- **Authentication:** internal service-to-service (ไม่ใช่ user token — ดูหมายเหตุ Authentication ด้านบน)
- **Input:** `user_id`, `current_time`
- **Output:** รายการ risk window ที่ตรงเงื่อนไข พร้อม flag ว่าถึงเพดาน nudge/วันแล้วหรือยัง
- **อ้างอิง:** FR2 (F5, F7), FR6 (F19, F20)

### B2. Send Nudge
- **HTTP:** `POST /api/nudges`
- **วัตถุประสงค์:** สั่งให้ Content & Tone Engine ประกอบข้อความ แล้วส่งผ่าน Notification Gateway ก่อนประกอบข้อความต้องเรียก G1 (Get Recent Message History) เพื่อเลือกเมนูทดแทน/ถ้อยคำที่ไม่ซ้ำกับที่เคยส่ง และหลังส่งสำเร็จต้องเรียก G2 (Record Sent Content) เพื่อบันทึก log ทางเลือกทดแทนที่เริ่มเสนอ (จังหวะ ณ ตอนไหน) ก็ขึ้นกับ `intensity_mode` เช่นกัน (fast-track เลื่อนไปหลัง 1-2 สัปดาห์)
  - **ช่องทางส่ง (FR2, FR11):** ตรวจสอบก่อนว่า user มี `PushSubscription` ที่ `is_active = true` อยู่หรือไม่ — ถ้ามี ส่งผ่าน **Web Push เป็นช่องทางหลัก**; ถ้าไม่มี (ไม่เคยอนุญาต/ถอน permission/ทุก subscription หมดอายุ) ให้ **fallback ไปส่งผ่าน Email** ไปยัง `User.email` แทน บันทึกช่องทางที่ใช้จริงลง `NudgeLog.delivery_channel`
- **Input:** `behavior_pattern_id`, `phase_id` (จาก Phase Tracker), `scheduled_time` (`user_id` อ่านจาก token หรือส่งมาจาก scheduler ถ้าเรียกแบบ internal)
- **Output:** `nudge_id` (สร้างระเบียน `NudgeLog`), `delivery_status`, `delivery_channel` (`web_push`/`email`)
- **Error case:** ส่งไม่สำเร็จทั้ง Web Push และ Email (เช่น push service ปฏิเสธและ email server ล้มเหลว) → บันทึก `sent_time = null` พร้อมเหตุผล ไม่ retry ไม่จำกัดจำนวนครั้ง (นโยบาย retry เชิงเทคนิคยังไม่กำหนด — ดูสมมติฐาน); Web Push ส่งไม่สำเร็จเพราะ endpoint หมดอายุ (HTTP 410 Gone จาก push service) → ตั้ง `PushSubscription.is_active = false` แล้ว fallback ไป Email ทันทีในคำขอเดียวกัน
- **อ้างอิง:** FR2 (F5, F6), FR6 (F19, F20), FR7 (F22, F23), FR11

### B3. Record Nudge Response
- **HTTP:** `PATCH /api/nudges/{nudge_id}/response`
- **วัตถุประสงค์:** บันทึกผลตอบสนองของ user ต่อ nudge ที่ส่งไป
- **Input:** `nudge_id` (path parameter), `response_type` (`accepted`/`declined`/`no_response`), `response_text` (optional)
- **Output:** `NudgeLog` ที่อัปเดตแล้ว
- **อ้างอิง:** FR2, FR5 (F16)

### B4. Update Nudge Preference *(Should — F8)*
- **HTTP:** `PATCH /api/nudges/preferences`
- **วัตถุประสงค์:** ให้ user ปรับเวลาส่งล่วงหน้าของ nudge เองในหน้าตั้งค่า (ระบบตั้ง default อัตโนมัติ 15-30 นาทีให้ตั้งแต่แรก — ยืนยันแล้ว เดิม open question 10.1)
- **Input:** `lead_time_minutes` (`user_id` อ่านจาก token)
- **Output:** ค่า preference ที่อัปเดตแล้ว
- **อ้างอิง:** FR2 (F8) — เลื่อน priority จาก Could เป็น Should ใน Feature List หลังปิด open question 10.1 (2026-08-29)

## กลุ่ม D — ให้กำลังใจ และ Controlled Cheat Meal (FR4)

### D1. Evaluate Quit-Risk Signal
- **HTTP:** `POST /api/internal/quit-risk/evaluate`
- **วัตถุประสงค์:** ตรวจสอบบทสนทนา/ประวัติการตอบสนอง nudge ล่าสุดของ user ว่ามีสัญญาณใกล้ล้มเลิกหรือไม่
- **Authentication:** internal service-to-service (เรียกต่อจาก A1 หรือ scheduler — ดูหมายเหตุ Authentication ด้านบน)
- **Input:** `user_id`, ข้อความล่าสุด (จาก A1) หรือประวัติ `NudgeLog.response_type`
- **Output:** `risk_detected` (boolean), `reason` (`keyword_detected`/`repeated_no_response`) — บันทึกเป็น `QuitRiskSignal` ถ้าพบ ระบบต้องตรวจทั้งสองสัญญาณร่วมกันเสมอ (ยืนยันแล้วว่าใช้กลไกผสม — เดิม open question 10.2)
- **อ้างอิง:** FR4 (F13)

### D2. Send Encouragement Message
- **HTTP:** `POST /api/encouragement-messages`

## กลุ่ม J — Motivation Profiling (FR10)

### J1. Submit Motivation Statement
- **HTTP:** `POST /api/motivation-profile/statements`
- **วัตถุประสงค์:** รับข้อความอิสระที่ user เล่าเหตุผล/แรงจูงใจที่อยากลดน้ำหนัก (ตอน onboarding หรือทบทวนซ้ำภายหลัง) ส่งต่อให้ Motivation Profiling Engine สกัดประเภทแรงจูงใจและจัดกลุ่มระดับความเข้มแข็งทางใจ ใช้กลไกเดียวกับ A1 (Submit Conversation Message) แต่ผลลัพธ์บันทึกลง `MotivationProfile` แทน `BehaviorPattern`
- **Input:** `motivation_statement_text`, `sent_at`, `context` (`onboarding` / `review`) — `context = review` ใช้เมื่อเรียกจากจุดทบทวนภายหลัง onboarding **เฉพาะ user กลุ่มแรงจูงใจอ่อนกว่า** (ถูกบังคับ, กลัวจากข่าว) โดย trigger จาก I2 หลัง `RewardUnlock` สำเร็จ (ยืนยันแล้ว — เดิม open question 10.11) — user กลุ่มเข้มแข็ง (เพื่อคนที่รัก, ตระหนักด้วยตัวเอง) ไม่ถูกถามซ้ำ ใช้ record ตอน onboarding ตลอดโปรแกรม (`user_id` อ่านจาก token)
- **Output:** `motivation_profile_id`, และอย่างใดอย่างหนึ่งต่อไปนี้:
  - `motivation_type`, `strength_level`, `referenced_target` (ถ้าสกัด/จัดกลุ่มได้ชัดเจน — สร้าง `MotivationProfile` ที่ `is_current = true` และตั้ง record เดิม (ถ้ามี) เป็น `is_current = false`)
  - `clarifying_question` (ถ้าข้อมูลกำกวมจนจัดกลุ่มไม่ได้ — บันทึก `needs_clarification = true`)
- **Error case:** ข้อความว่าง/ไม่เกี่ยวกับแรงจูงใจการลดน้ำหนัก → บันทึก log ปกติโดยไม่สร้าง `MotivationProfile` ใหม่; กรณีสกัดได้แต่จัดกลุ่มไม่เข้าเกณฑ์ 4 กลุ่มที่กำหนด → บันทึกเป็น `motivation_type = unspecified`, `strength_level = unspecified` แทนการเดา
- **อ้างอิง:** FR10 (F30, F31, F34)

### J2. Get Motivation Profile
- **HTTP:** `GET /api/motivation-profile`
- **วัตถุประสงค์:** ดึง motivation profile ที่ใช้งานอยู่ปัจจุบัน (`is_current = true`) ของ user เพื่อใช้ปรับความถี่/โทนการให้กำลังใจ และโยงข้อความกลับไปหาแรงจูงใจเดิม (ใช้ภายในโดย D2 และ Dashboard)
- **Input:** `include_history` (query parameter, optional, boolean — ถ้า true คืนทุก record ไม่ใช่แค่ record ปัจจุบัน) (`user_id` อ่านจาก token หรือ internal caller)
- **Output:** `motivation_type`, `strength_level`, `referenced_target`, `motivation_statement_text`, `recorded_at` (และรายการ history ถ้า `include_history = true`)
- **Error case:** ไม่พบ motivation profile ที่ `is_current = true` (เช่น user ยังไม่เคยตอบ หรือครั้งล่าสุดยังกำกวมค้างอยู่) → คืนค่าว่าง ไม่ block การทำงานของผู้เรียก (D2 ต้อง fallback ไปส่งข้อความโดยไม่อ้างอิงแรงจูงใจ)

- **Output:** `User.chronic_condition_disclaimer_acknowledged_at` ที่อัปเดตแล้ว
- **Error case:** เรียกทั้งที่ `User.has_chronic_condition = false` → ไม่มีผล (no-op) ไม่ถือเป็น error
- **อ้างอิง:** FR12 (F41)

## กลุ่ม L — Adaptive Symptom Easing (FR13)

### L1. Report Symptom Severity
- **HTTP:** `POST /api/symptom-easing/reports`
- **วัตถุประสงค์:** รับรายงานอาการของ user ผ่านบทสนทนาอิสระ (กลไกเดียวกับ A1) ในช่วงวันที่ 1-7 ของโปรแกรม ประเมินความรุนแรง และผ่อนปรนปริมาณคาร์บ/น้ำตาลที่แนะนำถ้าเข้าเงื่อนไข
- **Input:** `message_text`, `sent_at` (`user_id` อ่านจาก token; ระบบคำนวณ `program_day` เองจาก `program_start_date`)
- **Output:** `symptom_easing_event_id`, `severity_level` (`mild`/`moderate`/`severe`), `easing_applied` (boolean)
- **Error case:** `program_day` อยู่นอกช่วงวันที่ 1-7 → บันทึก log ปกติผ่าน A1 แทน ไม่สร้าง `SymptomEasingEvent` (เพราะ FR13 จำกัดขอบเขตเฉพาะช่วงนี้)
- **อ้างอิง:** FR13 (F43, F44)

### L2. Get Easing Status
- **HTTP:** `GET /api/symptom-easing/status`
- **วัตถุประสงค์:** ดึงสถานะการผ่อนปรนล่าสุดของ user เพื่อใช้ประกอบเนื้อหาของ B2/D2 (ปริมาณคาร์บที่แนะนำในข้อความ)
- **Input:** — (`user_id` อ่านจาก token)
- **Output:** `easing_active` (boolean), `latest_event` (optional — ข้อมูล `SymptomEasingEvent` ล่าสุด)
- **อ้างอิง:** FR13 (F43)

## สมมติฐาน/คำถามที่ต้องยืนยัน

- **กลไก authentication/session ที่แน่นอน (open question 10.13 ของ spec)** ยืนยันแล้ว: JWT Token ใน header สำหรับทุก operation ยกเว้น signup/login/Google Sign-In — token expiry/refresh flow ที่แน่นอนยังต้องกำหนดตอน detailed design
- **นโยบาย fallback Web Push → Email (open question 10.12 ของ spec)** ยืนยันแล้ว: B2/D2 ใช้ Email ทันทีเมื่อไม่มี active `PushSubscription` แบบไม่ถามซ้ำ ไม่เพิ่มช่องทางอื่น — logic ที่มีอยู่แล้วตรงกับนโยบายที่ยืนยัน ไม่ต้องปรับเพิ่ม
- นโยบาย retry ของ B2 (Send Nudge) เมื่อส่งผ่านทั้ง Web Push และ Email ไม่สำเร็จ ยังไม่กำหนด (retry กี่ครั้ง, ห่างกันเท่าไหร่) — เป็นรายละเอียดเชิงเทคนิคที่ควรตัดสินใจตอน detailed design
- Operation ทั้งหมดสมมติว่าเป็น request/response แบบ synchronous เพื่อความง่าย แต่ B1 (Evaluate Upcoming Risk Windows), D1 (Evaluate Quit-Risk Signal), และ I2 (Evaluate & Update Streak) ในทางปฏิบัติน่าจะถูกเรียกจาก scheduler/background process (เช่น cron job หรือ job queue ของ Node.js) มากกว่า user-facing request — ระบุ path เป็น `/api/internal/*` ไว้ล่วงหน้าเพื่อสื่อว่าไม่ใช่ public endpoint แต่ยังไม่ยืนยัน mechanism เชิงเทคนิคที่แท้จริง (HTTP endpoint ภายในเครือข่ายเดียวกัน vs message queue vs in-process function call)
- C2 (List Phase Definitions) ระบุเป็น `/api/internal/phase-definitions` เพราะยังไม่มีหลักฐานว่ามี actor ภายนอก (เช่น admin) เรียกใช้ผ่านระบบจริง — ตาม assumption เดียวกับ [[20260827-01-high-level-architecture|High Level Architecture]] หากในอนาคตมี admin panel ควรย้ายมาเป็น public endpoint ที่ต้องผ่าน admin authentication แยกต่างหาก
- B4 (Update Nudge Preference) ผูกกับ Feature F8 ที่ยัง priority "Could" — ใส่ไว้เพื่อความครบถ้วนของ contract แต่ไม่ควรเป็นด่านแรกที่ implement ใน MVP
- F1 (Set Intensity Mode) ยืนยันแล้วว่าเปลี่ยนได้ตลอดเวลาไม่จำกัดจำนวนครั้ง (เดิม open question 10.6) แต่ต้องผ่าน F3 (Preview) ก่อนเสมอเมื่อเป็นการเปลี่ยนภายหลัง — ยังไม่ยืนยันว่า frontend ควร block การเรียก F1 โดยตรงถ้าไม่เคยเรียก F3 มาก่อนในเซสชันเดียวกันหรือไม่ (`change_acknowledged` flag พึ่งพา client ส่งมาซื่อสัตย์ ไม่ได้ enforce ฝั่ง server ว่าต้องเรียก F3 มาก่อนจริง)
- G1/G2 (Message History) ถูกออกแบบเป็น operation แยกภายใต้ path `/api/internal/*` ที่ B2, D2, D3, H1 เรียกใช้ภายใน แทนที่จะฝังไว้ในแต่ละ operation โดยตรง เพื่อให้ logic การหมุนเวียนเนื้อหาเป็นจุดเดียวที่ใช้ร่วมกันได้ทุกประเภทเนื้อหา — ทีมเทคนิคอาจเลือก implement เป็น internal service/module call ภายใน Express app เดียวกันแทนการ expose เป็น HTTP endpoint จริงก็ได้ (path `/api/internal/*` เป็นแค่ตัวอย่างแนวทางหนึ่ง)
- กลไกหมุนเวียนเนื้อหาจริง (สุ่มจาก pool / AI generate สด / ผสม — open question 10.7) ยังไม่กำหนดใน G1/G2 เพราะทั้งสอง operation ทำหน้าที่แค่ "จำ" ประวัติที่ส่งไปแล้ว ส่วน logic การ "เลือก" เนื้อหาถัดไปเป็นความรับผิดชอบของ Content & Tone Engine ที่ยังไม่ระบุ implementation
- H1 (Get Downside Warning Content) สมมติว่าเป็น operation แยกที่ B2/D2 เรียกไปแนบเนื้อหาเสริม ไม่ได้รวมเข้ากับ B2/D2 โดยตรง เพื่อให้ทีมเทคนิคตัดสินใจได้เองว่าจะส่งคำเตือนพร้อม nudge ทุกครั้ง หรือแยกเป็นข้อความต่างหากเป็นระยะ — ยังไม่ยืนยันความถี่ที่เหมาะสมในการแนบคำเตือน (ถี่เกินไปอาจทำให้ user กังวล)
- I4 (Redeem Reward Unlock) สมมติว่า cheat day (reward_type = `cheat_day`) ไม่ต้องผ่าน D3 (ซึ่งออกแบบมาสำหรับเมนู cheat meal เฉพาะ) แต่เรียก I4 ตรงเพื่อ mark ใช้สิทธิ์ — ยังไม่ยืนยันว่า cheat day ต้องมีเนื้อหา/ข้อจำกัดเพิ่มเติม (เช่น คำแนะนำสำหรับวันนั้นทั้งวัน) ที่ต้องออกแบบ operation แยกหรือไม่
- J1 (Submit Motivation Statement) จัดกลุ่มแรงจูงใจเป็น 4 ประเภท/ระดับตามสมมติฐานของ FR10 ซึ่งยังไม่ผ่านการ validate จากนักจิตวิทยา/ผู้เชี่ยวชาญด้าน behavior change (open question 10.10 ของ spec) — logic การสกัด/จัดกลุ่มจริง (rule-based keyword หรือ AI classification ผ่าน Claude API) ยังไม่กำหนดในเอกสารนี้ เป็นความรับผิดชอบของ Motivation Profiling Engine ที่ยังไม่ระบุ implementation
- J1/J2 ยังไม่ยืนยันว่า user ต้องถูกถามแรงจูงใจ**ก่อน**หรือ**พร้อมกับ**การเลือก intensity mode (F1 Set Intensity Mode) ตอน onboarding — สเปกระบุไว้แค่ "ก่อนหรือพร้อมกับ" (FR10) ลำดับ UX จริงต้องยืนยันตอนออกแบบ conversation flow ของหน้า onboarding บน React frontend
- J1 รองรับ `context = review` ยืนยันแล้วว่าใช้จริงใน MVP (เดิม open question 10.11) เฉพาะกลุ่มแรงจูงใจอ่อนกว่า trigger จาก I2 หลัง `RewardUnlock` — ยังไม่ยืนยัน UX ว่า user จะถูกถามทบทวนผ่านช่องทางไหน (แทรกในแชทหลัก / pop-up แยก) เป็นรายละเอียดที่ต้องออกแบบใน detailed design
- D2 (Send Encouragement Message) เรียก J2 ทุกครั้งก่อนประกอบข้อความ ซึ่งเพิ่ม dependency ระหว่าง Content & Tone Engine กับ Motivation Profiling Engine — ยังไม่ยืนยันว่าควร cache motivation profile ไว้ระดับ session/request หรือเรียกสดทุกครั้ง (แนวทางเดียวกับสมมติฐานเรื่อง caching ใน Database Schema)
- `motivation_referenced` output ของ D2 เป็น field ที่เพิ่มเพื่อรองรับการวัดผลตาม metric ในหัวข้อ 4 ของ spec ("% ของข้อความให้กำลังใจที่โยงกลับไปหา motivation profile") — ยังไม่ยืนยันว่าต้องเก็บสถิตินี้แบบ aggregate ที่ไหน (เช่น ต่อยอดจาก `MessageHistory` หรือสร้าง log แยก) เป็นรายละเอียดที่ทีมเทคนิคควรตัดสินใจตอน detailed design
- Auth1 (Signup) ยังไม่กำหนดเกณฑ์ความปลอดภัยขั้นต่ำของรหัสผ่านที่แน่นอน (ความยาวขั้นต่ำ, ต้องมีตัวเลข/อักษรพิเศษหรือไม่) — เป็นรายละเอียดเชิงเทคนิคที่ควรตัดสินใจตอน detailed design โดยอิง NFR ความปลอดภัยบัญชีผู้ใช้ในหัวข้อ 9 ของ spec เป็นฐาน
- Auth4/Auth5 (Push Subscription) สมมติว่า frontend เรียก Web Push API ของ browser เพื่อขอ permission และสร้าง subscription object ก่อน แล้วค่อยส่งมาบันทึกที่ backend ผ่าน endpoint นี้ — flow การขอ permission (VAPID key generation/distribution) เป็นรายละเอียดเชิงเทคนิคของ Web Push API ที่ไม่ได้ระบุในเอกสาร API contract นี้ ควรระบุใน detailed design ของ Notification Gateway
