# Test Plan — Proactive Nudge ก่อนเวลาเสี่ยง

Test plan นี้ครอบคลุม flow "AI ส่งข้อความเตือนก่อนถึงเวลาเสี่ยง แล้วเสนอทางเลือกทดแทน" อ้างอิงจาก [[../../02-design/01-prototypes/20260827-01-user-journey-proactive-nudge|User Journey — Proactive Nudge ก่อนเวลาเสี่ยง]] และ [[../../01-requirements/01-spec/20260827-01-jaifit-ai-coach-metabolic-transition|Requirement Spec]] (FR1-FR11)

> **หมายเหตุ (2026-08-28 — Pivot ช่องทาง):** ระบบเปลี่ยนช่องทางจาก LINE Official Account เป็น **Web App** — ทุก test case ด้านล่างที่เดิมพูดถึง "ส่งผ่าน LINE" ให้อ่านเป็น "ส่งผ่าน Web Push Notification (หลัก) หรือ Email (สำรอง)" แทน logic การทดสอบเดิมไม่เปลี่ยน เพิ่มเฉพาะ TC ใหม่สำหรับ Account Signup & Login (FR11) ท้ายตาราง
>
> **หมายเหตุ (2026-08-29 — ปิด Open Questions รอบ 4):** เพิ่ม TC-28 ถึง TC-36 ครอบคลุม grace day ของ streak (FR9), Chronic Condition Screening (FR12), Adaptive Symptom Easing (FR13), การอธิบายผลลัพธ์ก่อนเปลี่ยนโหมดความเข้มข้น (FR6), Google Sign-In (FR11) และการถามทบทวนแรงจูงใจซ้ำหลัง reward (FR10) — ค่าตัวเลขยังใช้สมมติฐานเดียวกับ TC เดิม (ดูหัวข้อสมมติฐานท้ายเอกสาร) รายละเอียดเหตุผลดู [[../../05-log/20260829-log|log 2026-08-29]]

## ขอบเขต (Scope)

### อยู่ในขอบเขต
- การตรวจจับเวลาเสี่ยงและคำนวณเวลาส่ง nudge ล่วงหน้า (journey step A-B)
- เนื้อหาและโทนของข้อความ nudge รวมถึงทางเลือกทดแทนที่เสนอ (step D-E)
- เพดานจำนวน nudge ต่อวัน (step C)
- การตอบสนองของ user 3 รูปแบบ: ทำตาม / ปฏิเสธ / เงียบ (step F-I)
- การ trigger ข้อความให้กำลังใจแบบเร่งด่วนเมื่อไม่ตอบสนองต่อเนื่อง (step K-L)
- การเลือกโหมดความเข้มข้นตอน onboarding และผลของโหมดต่อจังหวะ/เนื้อหาข้อความ (step A0, FR6)
- ความหลากหลายของข้อความ/เมนูที่เสนอ ไม่ให้ซ้ำติดต่อกันหลายวัน (FR7)
- การเตือนล่วงหน้าอาการ/สถานการณ์ไม่พึงประสงค์พร้อมวิธีรับมือ (FR8)
- การนับ streak และปลดล็อก cheat meal/cheat day ตาม milestone (step M-N, FR9)
- การเก็บแรงจูงใจตอน onboarding และผลของ motivation profile ต่อความถี่/การโยงข้อความให้กำลังใจ (step AM, FR10)
- การสมัครสมาชิก/เข้าสู่ระบบ, การขอสิทธิ์ Web Push, และการ fallback ไป Email เมื่อไม่มี active push subscription (step S, FR11)
- Grace day ของ Reward System — streak พักได้ 1 วันก่อนตัดจริง (FR9)
- Chronic Condition Screening ตอน onboarding และ disclaimer แนะนำปรึกษาแพทย์ (step CC, FR12)
- Adaptive Symptom Easing เมื่ออาการแย่ลงมากในวันที่ 1-7 (FR13)
- การอธิบายผลลัพธ์ก่อนเปลี่ยนโหมดความเข้มข้นภายหลัง (FR6)
- การสมัคร/เข้าสู่ระบบด้วย Google Sign-In (FR11)
- การถามทบทวนแรงจูงใจซ้ำหลังได้รับ reward สำหรับ user กลุ่มแรงจูงใจอ่อนกว่า (FR10)

### นอกขอบเขต
- Flow ของ user ใหม่ที่ยังไม่มี behavior profile เพียงพอให้ detect pattern (journey ยังไม่ครอบคลุม ระบุไว้เป็นสมมติฐานใน journey ต้นทาง)
- ความแม่นยำของ NLU ในการสกัดข้อมูลจากบทสนทนาอิสระ (อยู่ในขอบเขตของ FR1 โดยตรง แต่ควรมี test plan แยกต่างหากเพราะเป็นคนละ layer)
- ค่าจริงของ threshold (เวลาส่งล่วงหน้า, เพดาน nudge/วัน, จำนวนครั้งไม่ตอบสนองที่ trigger สัญญาณเสี่ยง) เนื่องจากยังเป็น open question ที่ยังไม่ยืนยันในเอกสารต้นทาง — test case ด้านล่างใช้ค่าสมมติเพื่อทดสอบ "กลไก" ไม่ใช่ค่าที่ยืนยันแล้ว (ดูหัวข้อสมมติฐานท้ายเอกสาร)

## สมมติฐาน/คำถามที่ต้องยืนยัน

- ค่าตัวเลขในตาราง Test Data (เวลาส่งล่วงหน้า 15 นาที, เพดาน 3 ครั้ง/วัน, threshold ไม่ตอบสนอง 3 ครั้งติดกัน) เป็นค่าสมมติที่สร้างขึ้นเพื่อให้ทดสอบ "กลไก" ของระบบได้เท่านั้น ยังไม่ใช่ค่าที่ยืนยันจาก stakeholder — กลไก default lead time 15-30 นาทีและเพดานปรับอัตโนมัติตาม phase ยืนยันแล้ว (เดิม open question 10.1/10.3) แต่ threshold ตัวเลขจริงต่อ phase ยังต้องกำหนดตอน implement
- TC-32/TC-33 ใช้เกณฑ์ "เวียนหัวรุนแรงมาก" vs "มือสั่นนิดหน่อย" เป็นตัวอย่างแบบสมมติเพื่อแยก `severe` จาก `mild`/`moderate` — ยังไม่มีเกณฑ์ตัวเลข/คำที่ชัดเจนอย่างเป็นทางการว่าระดับไหนถือว่า "แย่ลงมาก" ตาม FR13 ต้องกำหนดก่อน implement จริง (ดูสมมติฐานเดียวกันใน Detailed Design)
- TC-30/TC-31 สมมติว่า Chronic Condition Screening เป็นคำถามปิด (yes/no) — ยังไม่ยืนยัน UX จริงว่าเป็นแบบฟอร์มปิดหรือบทสนทนาอิสระ
- TC-36 ใช้ User D (แรงจูงใจ "strong") เป็นกรณีเปรียบเทียบว่าไม่ถูกถามทบทวนซ้ำในสถานการณ์เดียวกัน — ควรเพิ่ม TC แยกยืนยันฝั่ง "ไม่ถามซ้ำ" ของ User D อย่างชัดเจนเมื่อ UX flow การถามทบทวนถูกออกแบบละเอียดกว่านี้
- TC-04 อ้างอิงตาราง phase ในหัวข้อ 8 ของ spec ซึ่งยังไม่ผ่านการ validate จากนักโภชนาการ/แพทย์ — ผลลัพธ์ที่คาดหวังของ TC-04 อาจต้องปรับตามคำแนะนำของผู้เชี่ยวชาญภายหลัง
- ยังไม่มี test case สำหรับกรณี user ใหม่ที่ไม่มี pattern เพียงพอ (ตรงกับที่ journey ต้นทางระบุว่ายังไม่ครอบคลุม) — ควรเพิ่มเป็น test plan แยกเมื่อ journey นั้นถูกออกแบบ
- ยังไม่ได้กำหนด "window ที่ยอมรับได้" ของความแม่นยำเวลาส่ง nudge ใน TC-01 อย่างเป็นตัวเลข (NFR ในหัวข้อ 9 ของ spec พูดถึงเชิงคุณภาพเท่านั้น) — ควรระบุตัวเลข SLA ที่ชัดเจนก่อนนำ TC-01 ไปทดสอบจริง
- TC-10 ถึง TC-13 (โหมดความเข้มข้น) — ความถี่ที่อนุญาตให้เปลี่ยนโหมดยืนยันแล้ว (เดิม open question 10.6): เปลี่ยนได้ไม่จำกัดจำนวนครั้งแต่ต้องอธิบายผลลัพธ์ก่อน (ดู TC-34 ใหม่) — TC เดิมยังครอบคลุมเฉพาะ flow การเลือกโหมดครั้งแรกและผลของโหมดต่อจังหวะ nudge
- TC-16 (เตือนล่วงหน้า) อ้างอิงเนื้อหาอาการที่ยืนยันแล้วว่าใช้สมมติฐานผู้ก่อตั้งไปก่อนใน MVP (เดิม open question 10.8) ยังไม่ผ่านการ validate จากนักโภชนาการ/แพทย์เป็นทางการ — ผลลัพธ์ที่คาดหวังอาจต้องปรับตามเนื้อหาที่ validate แล้วในอนาคต
- TC-17 ถึง TC-19 (Reward System) ใช้ค่าสมมติเรื่องกติกาการนับ/รีเซ็ต streak เพื่อทดสอบ "กลไก" — กติกา grace day ยืนยันแล้ว (เดิม open question 10.9) และมี TC-28/TC-29 ใหม่ครอบคลุมโดยตรงแล้ว
- TC-20 ถึง TC-23 (Motivation Profiling) อ้างอิงการจัดกลุ่ม 4 ระดับความเข้มแข็งทางใจที่ยืนยันแล้วเป็นฐาน (เดิม open question 10.10) แต่ AI มีความยืดหยุ่นปรับได้จากบทสนทนาจริง ยังไม่ผ่านการ validate จากนักจิตวิทยา/ผู้เชี่ยวชาญด้าน behavior change เป็นทางการ — ผลลัพธ์ที่คาดหวัง (เช่น การจัดกลุ่ม "weaker"/"strong") อาจต้องปรับตามเกณฑ์ที่ validate แล้ว
- TC-22 ยังไม่ระบุตัวเลขที่ชัดเจนว่า "ถี่กว่า" คือถี่กว่ากี่เท่า/กี่ครั้ง เป็นการทดสอบเชิงกลไกว่าความถี่แตกต่างกันจริงตามระดับแรงจูงใจ ไม่ใช่ค่าที่ยืนยันแล้ว
- Flow ทบทวนแรงจูงใจซ้ำหลัง onboarding ยืนยันแล้วว่าต้องมีสำหรับกลุ่มแรงจูงใจอ่อนกว่า (เดิม open question 10.11) — ครอบคลุมแล้วใน TC-36 ใหม่ ยังไม่มี TC แยกยืนยันฝั่ง "ไม่ถามซ้ำ" ของกลุ่มเข้มแข็งอย่างชัดเจน (ดูหมายเหตุที่ TC-36)
- TC-26 อ้างอิงกลไก JWT Token ที่ยืนยันแล้ว (เดิม open question 10.13) — "อายุ token ที่กำหนด" ยังไม่มีตัวเลขจริง เป็นการทดสอบกลไกเท่านั้น
- TC-27 อ้างอิงนโยบาย fallback ที่ยืนยันแล้ว (เดิม open question 10.12): ไม่มี push → ส่ง Email ทันทีแบบไม่ถามซ้ำ ไม่มีช่องทางอื่นเพิ่มเติม
- ยังไม่มี test case สำหรับกรณีทั้งสองช่องทางล้มเหลว (Web Push ส่งไม่สำเร็จ และ Email ก็ส่งไม่สำเร็จ) — ควรเพิ่มเมื่อมีการยืนยัน retry/error policy ที่แน่นอนของ Notification Gateway
