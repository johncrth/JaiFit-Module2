# สร้าง Product Backlog จาก Requirement

Skill นี้ใช้สำหรับแปลงเอกสารใน `docs/01-requirements/01-spec/` (และ `02-plan/` ถ้ามีผลต่อ priority) ให้เป็น product backlog ที่ทีมพัฒนาหยิบไปใช้ได้จริง โดยให้งานวิเคราะห์เชิงลึกไปที่ subagent `backlog-analyst`

## ขั้นตอน

1. **สำรวจข้อมูลตั้งต้น** — ดูว่า `docs/01-requirements/01-spec/` มีเนื้อหาอะไรอยู่แล้วบ้าง (Glob/Read) ถ้าแทบว่างเปล่า ให้สัมภาษณ์ผู้ใช้สั้น ๆ ก่อน เช่น:
   - กลุ่มผู้ใช้งานหลักคือใคร (ลูกค้า, พนักงาน, ผู้จัดการ ฯลฯ)
   - ฟีเจอร์หลักที่ต้องมีคืออะไร
   - ขอบเขตที่ไม่ทำ (out of scope) มีอะไรบ้าง
   - ข้อจำกัดทางธุรกิจ/เทคนิคที่ทราบแล้ว
   อย่าข้ามขั้นตอนนี้ไปเดาเอาเอง — ถ้าข้อมูลไม่พอ ให้ถามก่อนวิเคราะห์

2. **มอบหมายงานวิเคราะห์** — เรียก subagent `backlog-analyst` ผ่าน Agent tool พร้อมส่ง path ของเอกสาร spec ที่เกี่ยวข้องและ context ที่รวบรวมได้จากขั้นตอนที่ 1 ให้ subagent อ่านเอกสารเองและคืนผลเป็น backlog แบบ Markdown (epics → stories → acceptance criteria → priority MoSCoW → dependencies → สมมติฐานที่ต้องยืนยัน)

3. **นำเสนอผลลัพธ์** — แสดง backlog ที่ได้ให้ผู้ใช้ตรวจสอบ โดยเฉพาะส่วน "สมมติฐาน/คำถามที่ต้องยืนยัน" ให้เน้นย้ำว่าผู้ใช้ควรยืนยันหรือแก้ไขก่อนนำไปใช้จริง

4. **บันทึกลงเอกสาร (ต้องขอ confirm ก่อนเสมอ)** — ถ้าผู้ใช้ต้องการบันทึก ให้เขียนไฟล์ที่ `docs/01-requirements/03-task/backlog.md` (สร้างใหม่ถ้ายังไม่มี ใช้ Edit ถ้ามีอยู่แล้วเพื่อไม่ให้ทับของเดิมโดยไม่ตั้งใจ) แล้วอัปเดตลิงก์ใน `docs/01-requirements/03-task/index.md` ให้ชี้ไปยังไฟล์ backlog ตาม convention `[[wikilink|label]]` ที่ใช้อยู่ในโปรเจกต์นี้

5. **การแก้ไขภายหลัง** — ถ้าผู้ใช้ขอปรับ priority, เพิ่ม/ลบ story หรือแก้ acceptance criteria ให้แก้ไฟล์ backlog ที่มีอยู่ด้วย Edit แบบเจาะจงจุด แทนที่จะสร้างใหม่ทั้งฉบับ

## หลักการสำคัญ

- ห้ามใส่ requirement ที่ไม่มีหลักฐานในเอกสารหรือคำตอบของผู้ใช้ ให้ระบุเป็นสมมติฐานที่ต้องยืนยันแทนการเดาเงียบ ๆ
- รักษารูปแบบเอกสารให้สอดคล้องกับ convention เดิมของ `docs/` ในโปรเจกต์ (ภาษาไทย, โครงสร้าง index.md, wikilink อ้างอิงข้ามโฟลเดอร์)
- backlog ต้องจัดลำดับความสำคัญแบบ MoSCoW และระบุ dependency ระหว่าง story ที่มีผลต่อการวางแผนพัฒนา
